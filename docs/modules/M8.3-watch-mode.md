# M8.3: Watch mode (continuous live monitoring)

## In one sentence
One click (**Watch live** in the case file) keeps a case live. Unmask checks the attacker's wallets every block, reruns the whole analysis when money moves, puts a fresh alert in the approval queue for every new deposit at an exchange or mixer, and re-collects public posts every 10 minutes. Nobody has to press anything.

## Why
The problem statement asks for a system that *automatically* scrapes public sources and treats the *live* ledger as data. Before M8.3 the pieces existed, but nothing ran them together:
- a 12-second Alchemy poller, reachable only through the API;
- post collection behind a button;
- reruns behind a button.

## What happens while watching

```
every block (12 s)                          every 10 minutes (in the background)
──────────────────                          ────────────────────────────────────
check the watched wallets for new moves     collect news feeds + GitHub (+ Telegram)
  │ new transfers?                            │ new posts?
  ▼                                           ▼
store them (with their role: mixer, swap…)  ──► rerun the engine (under a second)
one alert per new exchange/mixer deposit         → money panel, exits, suspects and alerts update
                                                 → the case file refreshes by itself
```

| Case loaded | Where new transfers come from |
|---|---|
| **Real hack or Trace any address** | The real blockchain (Alchemy), from the current block onward. It watches up to 10 attacker wallets, the ones still holding money first. Needs `ALCHEMY_API_KEY`. |
| **Simulated attack** | The simulated attacker carries on. Every 30–40 s, one wallet that still holds money sends 10–25% of it to the exchange Unmask predicted. That's how a live demo shows alerts appearing on their own. It's labeled "simulated attack" on screen. |

Each new deposit at an exchange raises its own alert, for example: *"Just now: 28.16 ETH ($84,490) moved from attacker wallet 0x054c3b90… to Exch-A (0x1f223f41…). Ask their compliance team to freeze it."* As always, nothing is sent until a person clicks **Approve and send**.

Watching stops by itself after **30 minutes**, so a forgotten tab can't use up the free Alchemy quota. It also stops when another case is loaded, or when **Stop watching** is clicked.

## API

| Endpoint | What it does |
|---|---|
| `POST /api/live/start` | Start watching the loaded case (optional body `{"watch": ["0x…"]}` to choose wallets). Returns the status. |
| `POST /api/live/stop` | Stop. |
| `GET /api/live/status` | `on`, `source` (simulated/blockchain), `watching`, `checks`, `new_transfers`, `reruns`, `last_check_ts`, `last_posts_ts`, `posts_found`, `stops_ts`, the 8 most `recent` moves, and `error` if it stopped on one |
| `GET /api/live` | Server-sent events: every new transfer as it's stored (unchanged) |

## Files
- [backend/gt/watch.py](../../backend/gt/watch.py) (new): `watch_loop` (check → store → alert → rerun, posts on a timer), `chain_source` (real blockchain), `simulated_source` (the simulated attacker carrying on), and the per-deposit alerts.
- [backend/gt/api.py](../../backend/gt/api.py): start, stop and status endpoints. Post collection is shared with the **Collect public posts** button.
- [backend/gt/chain/live.py](../../backend/gt/chain/live.py): one kept-alive connection to Alchemy. The old `live_loop` was removed, because `watch_loop` replaces it.
- [frontend/src/console/LiveWatch.tsx](../../frontend/src/console/LiveWatch.tsx) (new): the toggle, the live numbers, the feed of new moves, and a case refresh after every rerun. It polls the status every 3 s.

## Problems found while testing, and fixed

| Problem | Cause | Fix |
|---|---|---|
| A real-hack watch didn't check the chain for 30+ seconds | Post collection (~25 s) ran before the first chain check | Posts are collected in the background; chain checks never wait (tested) |
| One check of 10 wallets took 20 s | Every Alchemy call opened a new HTTPS connection (~1 s each) | One kept-alive connection: ~8 s, and the wait counts check time, so it's one check per block |
| A second deposit to the same exchange raised no alert | Exit alerts are one per exchange address | Watch mode adds one alert per new deposit (`live:<tx>`) (tested) |
| **Three real security researchers became 23% "suspected" on Euler** | Their GitHub code quoted the hacker's address, and any mention counted as strong evidence (×30) | A mention counts only for an address that isn't a seed (seeds come from public post-mortems) and that only one person posted. An address several people posted is public knowledge: ×7.5 for two people, about ×1 for four or more. Euler's top "suspect" is now a news feed at 3%, the baseline. The simulated attacker, the only one who knows their test wallet, is still found (tested). |

Tests: 197 passing (new: `tests/test_watch.py`, the watch API tests, and the public-mention test).

## Verified in the browser (test stack, ports 8011/5181)
- **Simulated attack 7:** after **Watch live**, two moves to Exch-A appeared within a minute. The analysis reran by itself, "At exchanges" went from $21.2M to $21.4M, and two "Just now…" alerts waited for approval.
- **Euler (real chain):** watching 10 wallets on Ethereum, a check about every 12 s, 0 new transfers (correct: they've been quiet since 2023), and 174 posts collected in the background. **Stop watching** turned it off.

## Limits
- The watch runs inside the API process. If the server sleeps or restarts (Render's free tier sleeps after 15 minutes idle), watching stops and has to be started again. A paid always-on worker or a scheduled job would remove that.
- 10 wallets, 30 minutes per watch, ERC-20 and ETH transfers (not internal transfers), Ethereum only for the live check.
- The simulated feed always sends to the predicted exchange. It's a demo of the loop, not a model of the attacker.
